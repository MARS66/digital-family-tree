# 技术架构与开发路线

## 1. V1 推荐

- 前端：微信小程序原生框架 + TypeScript；UI 组件库按原型阶段选定。
- 后端：独立 Node.js + TypeScript 服务，采用模块化单体。
- API：REST/JSON，OpenAPI 作为契约；后台任务处理导入、查重、媒体。
- 数据库：PostgreSQL。
- ORM：优先 Prisma；若团队重视 SQL 可控性和轻量迁移，可选 Drizzle。
- 对象存储：腾讯云 COS，私有桶 + 短期签名 URL。
- 身份：微信小程序 code 换取 OpenID；有 UnionID 时作为跨应用辅助标识，内部始终使用 User UUID。
- 基础设施：腾讯云中国大陆区域；密钥由环境/密钥服务管理。

## 2. 独立后端 vs 微信云开发

| 维度                 | 独立后端 | 微信云开发             |
| -------------------- | -------- | ---------------------- |
| 起步速度             | 较慢     | 快                     |
| PostgreSQL/事务/约束 | 强、原生 | 取决于云开发能力与选型 |
| 复杂审核与导入任务   | 易于设计 | 可能受平台运行模型约束 |
| 可迁移性             | 高       | 较低，平台耦合         |
| 运维成本             | 较高     | 较低                   |
| 长期数据治理         | 更可控   | 适合简单场景           |

**V1 推荐独立后端 + PostgreSQL。** 理由不是流量规模，而是本项目的核心风险在关系一致性、审核事务、版本、导入和合并。独立后端更容易实现清晰的领域边界、数据库约束、后台任务与可测试事务。微信云开发可用于极快概念验证，但若选用也必须保持领域层和 API 契约独立，避免把业务逻辑散落在云函数。

## 3. Prisma vs Drizzle

- Prisma：数据模型直观、迁移与开发体验成熟、适合快速组建团队；复杂部分唯一索引、递归查询和 PostgreSQL 特性可能需要原生 SQL 迁移。
- Drizzle：更接近 SQL、类型推导轻、复杂约束更透明；团队需更熟悉数据库设计。

V1 默认 Prisma，并明确允许在迁移和关系查询中使用审查过的原生 SQL。若核心团队 SQL 能力较强，可在编码前用一个循环检测与部分唯一索引 spike 决定 Drizzle；选定后 V1 不混用 ORM。

## 4. 为什么暂不使用 Neo4j

当前主要访问是按 Family 限定的局部亲属查询，PostgreSQL 的邻接表、递归 CTE、索引与事务足以覆盖 1000 人级甚至更大规模。关系真实性、审核和版本也天然适合关系型数据库。未来若出现跨家族复杂路径、推荐或图分析，可通过事件/outbox 将规范化事实投影到图数据库；PostgreSQL 继续作为事实源。

## 5. 模块边界

- `auth`：微信身份、会话。
- `families`：家族、成员、分支与角色。
- `people`：人物、隐私、认领。
- `kinship`：亲子、伴侣、推导、循环/冲突校验。
- `contributions`：草稿、审核、正式应用、修订。
- `invitations`：token、二维码、接受。
- `imports`：上传、解析、映射、候选与确认。
- `quality`：查重、冲突、合并。
- `media/sources/events`：档案资料。

模块化单体内禁止跨模块直接改表，使用领域服务；合并、审核批准等跨模块操作通过应用服务协调同一数据库事务。

## 6. 数据层与任务

- PostgreSQL 是唯一事实源；Redis 可在确有会话、限流、队列需求时引入，不作为 V1 必选。
- 后台任务采用持久队列；任务记录 job ID、进度、重试次数和最终错误。
- 通过 outbox 表原子记录后续事件，避免“数据库已提交但消息未发”。
- 每日备份 + 时间点恢复能力；发布前做恢复演练。

## 7. 安全与可观测性

- 租户范围不可由客户端隐式继承；每个查询显式 family_id。
- 服务端字段级序列化，敏感字段加密；COS 私有访问。
- 上传白名单、大小限制、恶意文件扫描；Excel 解析防公式注入。
- 结构化日志含 trace ID、actor、family、action，不含敏感值。
- 指标覆盖接口延迟、5xx、审核积压、导入失败、重复/冲突率。

## 8. 测试策略

- 单元测试：亲缘规则、权限决策、隐私范围、状态机。
- 属性/生成式测试：随机关系图下不产生自环或祖先循环。
- 集成测试：PostgreSQL 真库、迁移、事务、部分唯一约束、并发批准。
- 契约测试：OpenAPI 与前端客户端一致。
- E2E：创建家族到审核扩张主闭环；邀请过期、越权、冲突、弱网重试。
- 性能测试：1000 人/3000 边，局部视图和审核列表。

## 9. 开发路线

1. **底层模型/API**：迁移、身份骨架、人物与亲子关系、循环/并发测试。
2. **创建家族**：登录到首人认领闭环。
3. **家庭补录**：草稿、家庭单元、来源、待审包。
4. **邀请/认领/审核共建**：三类邀请、角色范围、批准原子生效。
5. **家谱可视化**：权限过滤的三类局部 View。
6. **大规模补谱/导入**：Excel 管线、查重、冲突与人工确认。

每阶段的完成定义见 `MVP_SCOPE.md`，具体工程任务见 `CODEX_TASKS.md`。
